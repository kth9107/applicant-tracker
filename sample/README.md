# Ollama qwen3.5:4b 메일 파싱 테스트 케이스

헤드헌터 ↔ 인사담당자 간 채용 메일을 파싱하는 LLM 파이프라인의
**회귀 테스트 / 벤치마크용** 데이터셋입니다.

## 구조

```
test_cases/
├── schema.json                          # 모든 expected JSON이 따르는 스키마
├── 01_happy_path/                       # 정상 추천 (3개)
├── 02_sparse/                           # 정보 부족 (3개)
├── 03_rich/                             # 정보 과잉 / 다중 후보자 (2개)
├── 04_ambiguous/                        # 애매한 표현 (2개)
├── 05_noise/                            # 서명/광고/인용 (2개)
├── 06_adversarial/                      # 인젝션/엔티티 혼동/이중언어 (3개)
├── 07_wrong_domain/                     # 채용 메일이 아닌 경우 (3개)
└── 08_edge_cases/                       # 빈 메일 / 동명이인 / 손상 / 무구조 / 불합격 (5개)
```

총 **23개 케이스 × 2 파일 (입력 .txt + 정답 .expected.json)**

## 사용법

### 1. 베이스라인 측정
현재 운영 중인 파이프라인 코드에 각 `.txt` 파일을 한 번씩 흘려보고,
출력을 같은 이름의 `.actual.json`으로 저장합니다.

### 2. 비교
각 `*.expected.json`과 `*.actual.json`을 필드별로 diff 합니다.

### 3. 점수
케이스별로 다음 세 가지를 측정:
- **JSON parse 성공 여부** (true/false)
- **스키마 일치 여부** (jsonschema 라이브러리)
- **필드별 정확도** (이름/연도/회사 등 핵심 필드 일치율)

## 카테고리별 검증 목적

| 카테고리 | 잡으려는 모델 실패 패턴 |
|---|---|
| 01_happy_path | 베이스라인 — 여기서 실패하면 다른 거 볼 필요 없음 |
| 02_sparse | 빈 필드를 환각으로 채우는 경향 |
| 03_rich | 배열 길이 늘어나면 JSON 중간 절단 |
| 04_ambiguous | 추론 vs 원문 보존의 균형 |
| 05_noise | 서명/광고/인용 분리 능력 |
| 06_adversarial | 프롬프트 인젝션 저항, 엔티티 구분 |
| 07_wrong_domain | 도메인 분류 정확도 |
| 08_edge_cases | 빈 입력, 동명이인, 손상 데이터 견고성 |

## 다음 단계 권장

1. 현재 코드의 베이스라인 점수 측정
2. Ollama `format: "json"` 옵션 추가 → 재측정
3. JSON Schema 강제 (`format: {...}`) 추가 → 재측정
4. (선택) Instructor + Pydantic 도입 → 재측정

각 단계마다 점수 변화를 표로 비교하면, 어느 단계가 가장 효과적인지
**감이 아닌 데이터**로 알 수 있습니다.
